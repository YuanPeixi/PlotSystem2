# 工单23：运行中场景持久化与断线恢复

**优先级**：P1  
**依赖**：10、13、14 已完成  
**建议模型**：Claude Opus 5

## 1. 问题

场景运行时，新轮次只经 SSE 推送；`orchestrator.run_scene()` 要等整场结束后才调用
`repository.save_scene(scene)`。因此用户在模拟途中刷新、切换页面或遇到断线时，前端即使重新获取
`Scene`，也拿不到尚未结束的轮次；当前 `joinScene()` 还会再次调用 `/start`，把“重连”和“首次启动”混在一起。
进程异常退出后，数据库里的运行状态也缺少明确对账。

这不是单纯前端状态丢失：工单03只能恢复后端已经持久化的数据，本工单负责让运行中的真实进度可恢复。

## 2. 目标（Definition of Done）

1. 每个新 `DialogueTurn` 在 SSE 发布前或同时可靠写入 `Scene.dialogue_log`，刷新后可由场景详情接口补回；不得重复轮次。
2. 明确区分“首次启动场景”和“订阅/重连既有场景”。重连不得触发第二次模拟。
3. 提供前端可判断场景是否仍在本进程运行的信息，或等价的查询语义；保持【契约9】单进程假设。
4. 应用启动时对账遗留的 `running` 场景，避免永久显示运行中；不得擅自自动重跑 LLM。
5. 保持工单10的启动幂等、工单14的记忆继承顺序、场景前后快照语义以及 `data_json` 真相源契约。
6. 补充后端测试：逐轮落盘、断线补齐、重复启动不分叉、重启状态对账。

## 3. 建议实现边界

主要检查 `backend/services/orchestrator.py`、`backend/services/repository.py`、
`backend/api/scenes.py`、`backend/main.py` 和相关测试。可以新增窄用途 repository 方法，
但不要在 API 层写业务逻辑，也不要把进程内 `_active_scenes` 伪装成跨进程能力。

前端的分支/历史场景/快照导航、URL 恢复与导演决策恢复属于扩充后的工单03，不在本工单内。

## 4. 验收

运行一个多轮场景，在中途刷新或重新请求场景详情：已产生轮次可完整恢复且顺序、ID 唯一；
重连不会增加额外运行任务。模拟进程异常退出并重启后，遗留状态被明确修正，用户可再次显式启动或处理场景。
