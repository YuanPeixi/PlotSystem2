# 工单流程约定

> 本文件收纳 `docs/fix-tickets/` 的**流程规则**，从索引里抽出来，避免规则文字淹没工单表。
> 索引本体见 [README.md](./README.md)，排期理由与已合并 PR 的结论见 [NOTES.md](./NOTES.md)。

---

## 1. 工单怎么写

每份工单**独立、自包含**，可单独分发给任意 AI session，不依赖历史对话。

**写目标与判据，不写分步实现。** 实现步骤与精确行号会随代码过时，
而过时的“精确位置”比没有更糟；且过度具体的步骤会把执行者锁在你当时想到的方案上。
模型自己能推出来的不写，**只写它推不出来的**：你的意图、你已排除的选项、不能踩的线。

骨架（参考 [26-memory-write-watermark.md](./26-memory-write-watermark.md)）：

| 节 | 内容 |
|---|---|
| **现象** | 用户可见的故障是什么、触发条件 |
| **为什么必须修** | 不修的代价（尤其是“不会自愈”“静默”这类） |
| **判据（DoD）** | 什么算修好了，可验证 |
| **红线与已排除** | 不许碰什么 + 考虑过但否决的方案及理由 ← **最防返工的一节** |
| **验收** | 怎么证明不是假通过（见 §7） |
| **线索** | 大致模块/关键词，**不写行号**；列出易漏的同步项 |

编号：01–15 沿用原编号；16 起为新增，部分文件尚未创建（索引中标「待建单」）。
已完成的工单**冻结不改**（它们是历史记录），旧工单只在下次开工时顺手转新骨架。

## 2. 状态口径

| 状态 | 含义 |
|---|---|
| `待处理` | 工单文件已写，尚未进入开发 |
| `待建单` | 连工单文件都还没写 |
| `⏳ 等待 PR（分支）` | 改动已在指定分支完成，尚未创建 PR |
| `🔍 审核中（PR #N）` | PR 已创建，正在审核或等待合并 |
| `✅ PR #N（合入 main：a到b）` | PR 已合入，提交范围见 §3 |

这套格式的目的是避免把"已实现""已合并""等待审核"混为一谈。

分支名、PR 编号、提交范围一律**以实际 Git/GitHub 状态为准**；索引里的标注可能滞后。
如果因为 `gh.exe` 没有登录而无法核实，提醒用户自行操作或检查即可，不要猜。

---

## 3. hash 填写规则（踩过坑）

**提交范围里的 hash 必须是 `git log main` 里能查到的 main 原生 hash**，
不能抄 PR 页面或来源分支上的 hash。

原因：owner 分支若走 rebase 或 squash 合并，合入后 main 上的 commit hash 会和分支上的不同；
来源分支一旦删除，旧 hash 就变成死链（2026-08-24 在工单 11 / 15 / 17 三条上踩过，已订正）。

提交范围本身可选，但当 rebase 造成线性历史、难以从日志辨认归属时**必须**填写。

---

## 4. 开工流程

开始改动前先 `git checkout -b` 建分支，改完立即 commit 到该分支。

**不要把改动堆积在 `main` 上等最后再一次性搬迁** —— 既避免与他人并行改动冲突，
也让状态列的「⏳ 等待 PR（分支）」在任意时刻都能对应到一个真实存在的分支。

**合并策略**：owner 自己的改动 rebase / fast-forward 进 main（无 merge commit）；
组员的改动走 merge commit（“Merge pull request #N”）。
目的是让 `git log --graph` 尽量保持一条直线。

未推送的提交可放心 `git commit --amend`；**已推送就不要 amend**。

---

## 5. 核实“某分支是否已进 main”

**不能用 `git branch --merged`** —— rebase 后 hash 变了，它检测不到。

用 `git cherry origin/main origin/<branch>` 按 patch-id 比对：**全部前缀为 `-` 才是已等价合入**。

---

## 6. 收尾流程

PR 审核期间允许只写分支名或 `🔍 审核中（PR #N）`、**不填 hash** ——
main 上此时还没有对应提交，填了也是错的，这个粒度已经足够指引测试人员。

但 **PR 合入 main 后，必须当场用一次独立的 docs commit** 把该行状态改成
`✅ PR #N（合入 main：起始hash到结束hash）`。

不要拖到"下一个工单顺手更新"：rebase 合并的来源分支通常会被删除，
拖得越久、旧 hash 死链和状态滞后的窗口就越长，且下次改动者未必知道该去核对。

---

## 7. 测试与验收陷阱（踩过的“假通过”）

写验收用例前先看这三条。它们的共同点是：**用例绿了，但根本没走到被测分支。**

1. **验证“写入去重”时不要让 mock 每轮返回同一句固定文本** —— 同一发言者不同轮次会
   产生完全相同的字符串而被误判为重复写入。用 `side_effect` 给每轮不同文本。
2. **多个用例复用同一个 `scene_id` 会命中 `decisions` 表的幂等重放**，根本没调到 LLM。
   `tests/test_orchestrator.py` 的 `_setup_project_scene_and_snapshot` 已加 `suffix` 参数。
3. **验证“回滚不抹掉共享长期记忆”必须先建 `chroma_db` 再打快照**，
   否则快照不含 `chroma_checkpoint`，旧代码的 restore 也不会删任何东西。

另见 [NOTES.md#t08](./NOTES.md#t08)：测长期记忆隔离时如何用假向量避开真 embedding，
以及为什么必须断言 `long_term._collection is not None`。

## 8. 收尾 checklist

完成一个工单后按单勾一遍。**这五处漏一处，文档就开始撑谎，而撑谎的文档比没有文档更贵。**

- [ ] **代码 + 测试**：新增用例已避开 §7 的三条“假通过”
- [ ] **`CLAUDE.md`**（条件：碰了契约 / 数据模型 / API / 链路）
      —— 改数据模型走 §5.4 三步 checklist；修掉 §12 的缺陷或落地 §13 的设想要**从清单里删掉**并升格到正文
- [ ] **`.env.example`**（条件：新增配置项）—— 它是配置的唯一真值
- [ ] **`NOTES.md`**（条件：有 review 教训或设计决策）—— 带上 `<a id="...">` 锚点
- [ ] **`README.md` 状态行**：总是要改；**PR 合入 main 后当场一次独立 docs commit**（§6）

条件项不适用时直接跳过——**这张表的价值在于把“记住 5 个地方”变成“照单勾一遍”。**
