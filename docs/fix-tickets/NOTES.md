## 项目背景速览（给不熟悉本项目的 session）

- 项目：`PlotSystem`，多分支多智能体剧情推演系统。后端 FastAPI（`backend/`），
  前端 Vue3 + Vite + Pinia（`frontend/`）。
- **先读根目录 `CLAUDE.md`**：第 7 节九条契约是承重墙，
  第 12 节列出的已知缺陷与 dead code **不要顺手修**。
- 核心链路：实体抽取建图 → 角色卡生成 → **自研**场景引擎驱动多角色对话（非 AutoGen GroupChat）
  → 导演评估决策 → 快照/分支 → 总结输出。
- 数据存储：SQLite `data/projects.db`（`data_json` 列是唯一真相源）+ 角色卡 JSON 文件
  + Kuzu 嵌入式图库（单文件）+ ChromaDB 向量库。
- 启动：`npm run dev`（前后端同起）；单独：`npm run backend` / `npm run frontend`。
- 测试：`python -m pytest -q`（全量跑可能因 chromadb→onnxruntime 触发 DLL 崩溃，
  可单跑不涉及 chroma 的文件）。

## 工单 11 — 从「Selector + 环境交互」拆成两单

原 11 同时包含「Selector 发言模式」与「动作/环境交互裁决」，二者体量与风险完全不同。
现拆为：**11 = Selector 打通（纯修复，已完成）**，**20 = 环境智能体（大提案，见阶段 D）**。

**实现方案是独立评分**（`backend/scene_engine/speaker_selector.py`）：
对每个候选角色各发一次轻量打分调用（`asyncio.gather` 并行，整轮延迟仍是一个 RTT），
一次只让打分器看一个角色，从而消除旧实现"把所有名字排成一列问 LLM"带来的位置偏见，
以及 `agent.name in choice` 子串包含的误匹配。

LLM 输出的三维分（发言欲望 / 相关度 / 主动性）再叠加两个纯本地信号：
被直呼其名加分（最长名优先匹配）、几何衰减的重复发言惩罚（压低但不硬禁连续发言）。
打分器有独立接入点（`LLM_MODEL_SELECTOR` / `LLM_SELECTOR_BASE_URL` / `LLM_SELECTOR_API_KEY`），
可挂本地小模型。

兜底全部可观测：单个候选失败取其余人的中位数、全部失败退化为纯本地打分并 warning，
不再静默回退 `agents[0]`。链路已打通：`Scene.speaker_mode` → 反序列化 → API/导演规划
→ `run_scene` 构造 `SceneConfig` → `apply_decision` 的 rollback 重演场景，
缺省值取 `settings.DEFAULT_SPEAKER_MODE`。非法取值在 `CreateSceneRequest`（422）
与 `Settings.DEFAULT_SPEAKER_MODE`（启动即失败）两处拦截，引擎兜底回退时 warning 一次。
降级还会写入 `DialogueTurn.selector_notice`，前端在角色名后以灰字展示（如"服务不可用：降级选择"）。

**未做（有意留下）**：让角色先生成一句草稿再竞价 —— 需要 N 次角色模型调用/轮，
成本约等于场景本身翻 N 倍，收益不确定，待 selector 跑出实测数据后再评估。

## 工单 16 — Kuzu 快照持久化（已修复，留档）

这曾是排期里最容易被漏掉的坑，直接决定工单 06 能不能做：

- `GraphManager.checkpoint_to()` 用 `shutil.copytree()` 复制 `kuzu_db`，
  但当前 Kuzu 版本下 `kuzu_db` 是**单个文件**（实测 19–21 MB），不是目录 → 必抛 `NotADirectoryError`；
- 该异常被 `SnapshotManager.create_snapshot` 的 `except Exception → logger.debug` **静默吞掉**；
- 结果：`Snapshot.graph_checkpoint` 恒为空字符串，`restore_snapshot` 因找不到 checkpoint 而跳过，
  **快照从不包含知识图谱，回滚也不恢复图谱**。

**为什么当时不是 P0**：图谱只在 GraphRAG 构建阶段写入一次，之后全程只读。
既然内容不变，"回滚不恢复图谱"与"恢复了图谱"在效果上等价，因此当时无实际影响。

**修复内容（PR #15）**：`checkpoint_to` / `restore_from` 已按 `Path.is_dir()` 分支选择
`copytree` / `copy2`（新增模块级 `_remove_path` 处理删除），`create_snapshot` /
`restore_snapshot` 两处吞异常的 `logger.debug` 已提升为 `logger.warning` ——
**这个 bug 正是被日志级别藏起来的**。工单 06（动态图谱写回）的硬前置已解除。

## PR #15 — 为什么 23 / 03 / 19 / 16 合在一个 PR

四者是同一个用户可见故障的不同切面 —— "刷新一下推演数据就没了、快照功能几乎没用"。
拆开后任一个单独合入都不能让该场景可用：

- **23** 让后端真的有东西可恢复（逐轮落盘 + 状态对账）；
- **03** 让前端能找到并重连那些场景；
- **19** 让刷新后的决策状态不会退化成重复提交；
- **16** 则是快照面板上线后立刻暴露的真实缺陷。

审核时建议按"后端可恢复性 → API 新增/语义变化 → 前端重连与快照面板"三段看。

**留下的尾巴**：工单 03 的可选目标 6（创建场景时把 `scene_id` 写回 `Branch.scenes`）未做，
该字段仍恒为空数组；前端改用 `GET /projects/{id}/scenes?branch_id=` 查，不依赖它。

另外 PR #15 的 review 把 `fork_branch()` 里的 `restore_snapshot()` 拿掉了 —— 分叉本是
"开一条新 IF 线"，不该当场把主线的图谱与 Chroma 长期记忆就地回滚掉（这两者按项目共享、
不随分支隔离）。**因此分叉当时只登记来源快照**，新分支首场如何承接该快照、
`fork_conditions` 如何生效，归工单 08（已随 PR #16 落地）。

工单 08 已按此重写：先给分叉下严格定义（五条不变量 I1–I5），再分两阶段落地 ——
阶段 A 给长期记忆补分支维度（隔离性 I3 的架构前提），阶段 B 把 `fork` 与 `rollback`
收敛成同一个原语。**只改 `fork_branch()` 修不了这个问题**，原因见该工单 §1.2。

## 导演的三层目标模型（27 → 04 → 28 → 18）

2026-09-03 复核得出的结论是：导演目前既"瞎评"又"健忘" —— 评估时拿不到角色卡，
规划时只看得到最近 5 条场景标题，而 `narrative_goal` 是一个**只活一次 HTTP 请求的参数**，
在 `apply_decision` 里直接被 `f"延续上一场（{name}）的剧情走向"` 替换掉，
连跑几场后系统只剩动量、没有引力。四张工单分工：

- **27** 抽出公用的上下文压缩（导演侧目前零预算，总结侧按字符截尾会丢结局）
- **04** 修掉评估空转与一批 P0 bug
- **28** 立只读的故事目标锚点与可观测度量
- **18** 给导演路线图与长期记忆

**顺序不可调**：没有 28 的锚点，18 的路线图就没有对齐对象。

### 三层的具体分工与两条设计禁令

三层 = **项目级只读锚点**（`narrative_goal`）/ **分支级路线图**（`storyboard.outline`，
导演可写留痕）/ **场次意图**。做 28 / 18 前必读以下两条（讨论已定，不要重新评估）：

1. **不允许导演修改 `narrative_goal`**。它既是评分基准又可被被评方改写的话，
   自评系统会把目标改成自己刚演出来的东西，度量归零。导演的可写空间只在第二层。
2. **不新增 `DecisionType.END`**。它会波及决策 CAS、幂等表与前端三处；
   结局用 `is_ending_reached` 标志表达即可。

### 28 落地时定下的口径（18 会直接继承，别再重新讨论）

工单 DoD 里没写、实现前与用户逐条确认过的选择：

| 议题 | 结论 | 理由 |
|---|---|---|
| 进度历史存哪 | **不新增存储**，评估时现算 | 分支级/项目级字段都要额外维护一份状态；现算天然跟随谱系 |
| 谱系怎么取 | `Scene.parent_scene_id` 链 + 同分支历史的并集 | 该链按不变量 I4 跨分支接上，IF 线不必从 0 重爬；手建场景链会断，故并入同分支 |
| 停滞怎么记 | `story_progress_raw` + `progress_stalled` 布尔，**不存累计次数** | 累计值又是一份跨场状态；要聚合让消费方按分支自己算 |
| `story_progress` 不可用 | 用 `-1`，且**不进** `is_evaluation_unavailable()` | 那个函数意为"整份评估作废"，漏一个键不该连带把决策打成保守默认 |
| plan 接口的用户输入 | 语义收敛为**本场意图** `scene_intent`，主线目标固定读 project | 保留成"临时覆盖主线目标"会让锚点形同虚设 |
| 目标可否事后改 | 新增 `PATCH /projects/{id}` | 建项目时种子还没传、角色还没抽出来，目标往往写不准；这是用户侧写入口，不违反禁令1 |
| 双空时的结局判定 | `narrative_goal` 与 `ending_criteria` 都为空则**强制 False** | 没有锚点时导演唯一能对照的就是自己刚演的内容 |
| 结局达成后的前端 | 保留三个决策按钮，另加提示与输出入口 | 结局是导演的判断，用户可以不认同；别让一个布尔值锁死操作 |
| 线索谁合并 | 导演输出更新后的完整列表，后端只去重截断 20 | 只有导演知道哪条本场被收束了 |

**验收 3（跑题对白使 `plot_deviation_score` 升高）需要真 LLM，不适合进单测**：
自动化只断言"主线目标确实进了 prompt"，偏离度的真实敏感度留人工手测。

### 28 的 PR review 教训（5 条，全部为真）

前两条的共同点是**新增的状态自己没有"归属"信息**，于是被跨语境复用：

1. **进度是相对于目标的，就必须记住是哪个目标**。加了 `PATCH` 让用户能改主线目标后，
   单调钳制会拿旧目标下的 0.9 把新目标的真实进度永久钳到顶。已加
   `models.goal_revision()`（目标文本的 sha256 前缀）并记进 `SceneEvaluation`，
   只继承同版本的进度。**以后再加任何"跨场累积的度量"，先问它依赖哪个前提、前提变了怎么办。**
2. **"空列表"不等于"还没找到"**。`if not threads and evaluation.unresolved_threads` 把
   导演显式给出的空表（= 线索都收束了）当成没找到，继续往前取回更早的列表，
   已收束的线索被复活并写进下一场提示词。必须用独立的 `threads_found` 标志。
   这和 4.2 陷阱 14/16 的 `-1` 是同一族缺陷：**"无值"与"零值"必须能区分**。
3. 结局判定号称"基于主线目标 + 全部历史"，但 prompt 里只有本场对白 —— 跨场次达成的
   结局条件根本判不了。已把谱系上的 `evaluation.synopsis` 经 `fit_lines` 压缩后传入。
4. `bool("false") is True`：LLM 输出合法 JSON 的字符串布尔就能"结束"整个故事。
   已改为严格解析（真布尔 / `"true"`/`"false"` / 0/1），其余记 warning 回退 False。
5. 前端编辑草稿没有归属项目：编辑 A → 点开 B → 保存，会把 A 的文字写进 B 的锚点。
   已加 `editingProjectId` 并在切项目时清空草稿。

**第二轮又抬出两条（同样属实）**：

6. **限条数 ≠ 限预算**。`unresolved_threads` 只截到 20 条，单条可以无限长；
   而它会落库并逐场回喂，写进去一次就永久拖着。这正是 PR #17 已经确立过的
   “预算是硬约束，不是结果非空”—— **定了一条原则，要回头看自己新写的列表类字段是否也适用。**
7. **先钳后判会把 NaN 变成满值**。`max(0.0, min(1.0, nan))` 返回上界，
   `json.loads` 默认接受裸 `NaN`/`Infinity`，`float(True)` 也是 1.0。
   一个 NaN 就能变成“主线 100% 完成”或“满分 10”并直接进决策阈值。
   同族缺陷还在工单04 写的 `_score()` 里（reviewer 未提及，一并修了）。
   已统一走 `_parse_number()`：拒 bool + `math.isfinite`。

**第三轮三条（一条是本 PR 引入、一条是本 PR 的收尾、一条是被本 PR 放大的旧缺陷）**：

8. **血缘可追溯 ≠ 血缘可继承度量**。工单 08 的不变量 I4 只要求 `parent_scene_id`
   能把分支接回来源场景，它**不区分分叉在那一场的 before 还是 after**——在 08 的语境下
   无所谓，因为没有任何消费方把这条链当作"历史"来读。本 PR 的 `_story_context`
   是第一个消费方，于是把一个更强的语义（"父场景已经演过"）强加到了一条只保证弱语义的链上。
   典型失效：`apply_decision` 里 rollback 的默认目标就是 `scene.snapshot_id_before`
   （**主路径，不是边角**），于是"我不满意第 5 场，回滚重演"产生的 IF 线，
   继承了原线第 5 场演出来的进度与线索 —— 进度只升不降，这条线被永久钳在一个
   从未发生过的高度上，还被要求去收束本线没埋过的伏笔。
   首轮 `_lineage_cutoff` 仅处理分叉首场；进入下一场或再次分叉后，祖先遍历仍会
   重新读入撤销的结果。现改为快照时点历史副本，并在分叉/next_scene 时复制到场景。
   旧快照没有历史副本时 warning + 空历史，不能用来源最新评估伪造过去。
   **血缘链、快照时点、当前评估是三个不同概念，必须显式表达继承边界。**
9. `OverflowError` 是 `float()` 的第四种失败方式。第 7 条只接了 `TypeError/ValueError`，
   而 `json.loads` 把裸的超大整数（`1` 后跟几百个 `0`）解析成 Python `int`，
   `float()` 对它抛的是 `OverflowError`。漏接会穿过 `_extract_json` 那道防线，
   把一份本可解析的评估废在编排层的兜底里（`scene_error` / `fatal: False`）。
10. **导演台"生成结局输出"不带分支**（旧缺陷，本 PR 只是让它更容易被撞上）。
    跳去 `Output.vue` 后分支下拉框停在"全部分支"，用户在 IF 线上判定的结局，
    导出的是另一条时间线的故事。入口是 28 新加的，但同一个洞在 `CLAUDE.md` §9
    早有对应规则（"决策后要把分支选择一起切"）——**新增跨页跳转时，
    先去看目标页有哪些需要显式携带的上下文维度。**
    已在 query 里带 `?branch=`，且 `Output.vue` 等分支列表回来后才校验预选
    （分支可能已被删；预选一个不在下拉框里的值会让 select 显示空白而 `branchId` 仍失效）。

   后续收尾同时禁止加载期间生成，无效分支要求明确重选，加载失败提供重试，
   防止空默认值被发送成“全部分支”。

### 主线目标为空时的口径（2026-09-28，PR #21 合入后补）

**来由**：28 之前规划必须填目标（前端 `if (!goal.trim()) return` + 后端必填字段）。28 把目标挪到
项目上、规划输入改为可选的本场意图，却没有补一道"项目有目标或至少有意图"的替代门槛——
于是种子文本之外什么都不给，导演也能自己规划、直接开跑。18 又把它放大了一层：没有锚点时，
导演自拟的路线图会成为事实上的目标，而评估 prompt 带着它，被评方拿自己写的路线图给自己打分，
是禁令1 的另一个入口。

| 议题 | 结论 | 理由 |
|---|---|---|
| 要不要拦 | **只提示不拦**：规划前弹一次确认，同一项目只问一次 | "先看看角色自己会演出什么"是正当用法；硬门槛会砍掉它。28 验收 1 只要求老项目能读，不要求能规划，两者都不冲突，这是产品取舍 |
| 推进度 | 目标去空白后为空 → `PROGRESS_UNAVAILABLE`，不是 0，也不收自评 | 没有尺子谈不上推进；照收的话单调钳制会让进度一路爬向不存在的终点 |
| 其余评分 | 照常保留，另记 `SceneEvaluation.goal_missing`；前端对"目标达成""主线偏离"不判红、标"无锚点" | 只有对照目标的两项失去参照，张力与一致性不受影响，整份评估不能因此作废（与 `-1` 分区分） |
| 决策阈值 | `goal_missing` 时"目标达成 < 4 → 回滚"不生效，一致性规则照常 | 界面路径总带人工决策、走不到阈值规则，但 12（AutoPilot）会真的据此建分支 |
| 结局标准 | 只看主线目标，结局标准不算推进度的锚点 | 它只锚定"何时结束"，不告诉导演路走到了哪；结局判定仍按"双空才判否"（28 口径不变，只是空白也算空） |
| 老记录 | 按 `goal_revision == goal_revision("")` 回填，没有版本的更老记录不猜 | 恰恰是"没填目标就跑起来"的那些项目最需要看到无锚点提示 |

**不做**：不让分镜稿在空目标时停写（路线图对连贯性仍有价值，问题出在拿它当评分依据，
由评估 prompt 明确禁止）；不把空目标的版本改成空串来省掉 `goal_missing` 字段（空串已是
"旧记录、不参与继承"的标记，两者撞在一起，老记录与空目标就会互相继承进度）。

**合入方式**：按快速修复处理，不开 PR。经一轮独立 review（结论可合并，无确认级问题；
后端 369、前端 34 项测试全过）后，以 `--no-ff` 合并提交 `合入 fix/empty-narrative-goal`
直接进 main，溯源以该合并提交为准（`git log --first-parent main`）。此处不写 hash：
文档随合并一起提交，写不进合并提交自身的 hash。

## PR #18 — 28 收尾的 review 教训

落地内容：用 `Snapshot.story_history` / `Scene.inherited_story_history` 的**时点冻结副本**
替换上一版 `_lineage_cutoff` 的逐边截断（旧实现要在每条谱系边上判断分叉发生在 before
还是 after，语义脆弱）；`_deserialize_scene` 与 `get_snapshot` 还原 `created_at`。

review 抓出的教训，四条值得记住：

1. **新引入一个可继承字段，必须把它的每条写入/读取路径都走一遍。**
   `inherited_story_history` 有四条：首次冻结、continue 续跑、从它再分叉、并发改写。
   patch 只把首次冻结想周全了，于是留下"冻结副本和回溯之间不去重"的缺陷 ——
   它在 continue 重跑后再分叉时，让同一场评估进两次提示词。
   （同一处的"续跑沿用陈旧副本"是**误判**，见下方第 5 条。）
2. **写入侧做对了不等于读取侧也对。** `director_agent._normalize_threads` 的注释明确
   写着"LLM 未给出该键时沿用上一场的列表"，但读取侧 `_story_context` 用
   `ev.get(key, [])` 把"漏键"和"空列表"压成了同一个值 —— 而 §4.2 陷阱 17 恰恰要求
   两者必须能区分（空列表是"线索都收束了"的权威值）。
   **同一语义分散在读写两侧时，要成对检查。**
3. **降级要成片，不要留唯一的硬失败点。** 新加的 `created_at` 解析是
   `_deserialize_scene` 里唯一会抛 `ValueError` 的字段，一行坏数据能让整个
   `list_scenes` 五百，而同函数其余字段一律 `.get(默认值)`。
4. **写了测试不等于有测试。** 新增的 6 个前端测试没有任何 npm 脚本能选中它们
   （`scripts` 只有 dev/build/preview），`node --test tests/` 目录入口解析还会失败。
   已补 `npm test`。**新增测试必须确认它能被某条命令选中。**
5. **修 bug 前先证明 bug 存在 —— 否则"修复"本身就是新 bug。**
   第二轮 review 打回了第一轮的一条修复：我读到"continue 续跑会沿用陈旧冻结副本"
   便把 `inherited_story_history` 置 `None` 让它重新冻结，既没构造复现也没验证
   原缺陷是否真实。实际上本场评估**本来就会刷新**（副本不含本场，回溯时现读，
   而 `save_evaluation` 是 `INSERT OR REPLACE`），要修的东西不存在；而置 `None`
   把哨兵当指令用，反手打开两个真洞（来源快照被删 → 历史归零；来源后补评估
   → 越过边界渗入）。**动词要选准**：想刷新本场，却写成了丢弃整份继承。
   一并记住：`None` 型哨兵字段在改写前必须先问"它对读取侧意味着什么"。

另有一条**存量**缺陷由本 PR 的新测试首次暴露：`branch_memory.mark_fork_initialized`

3. 写入幂等走内容寻址 ID（`long_term.memory_id`，sha256）+ **先 `get` 判存在再 `upsert`**。
   前置判断不是优化：chromadb 0.5.20 的 `upsert` 会无条件重算 embedding，而 embedding 是

4. 顺带改名 `CharacterAgent.update_state_after_scene` → `consolidate_memory()`：

## 工单 12 — AutoPilot：与原单的偏离

原单写于 13 之后、08/18/28 之前，开工时按当前代码重写（分支 `feat/auto-pilot`）。
三处产品决定由 owner 拍板：**一次性会话**而非持久开关；回滚**允许连续 N 次（可配，默认 2）**；
continue **不单独限次**，只受总步数约束。

与原单不同的实现点及理由：

1. **会话不落库**（原单：`Project.auto_pilot` + `auto_pilot_max_chain`）。`PATCH /projects` 是整份
   读-改-写，逐步写计数会与用户编辑主线目标互相抹掉；落库后重启对账把场景置 paused，开关却还开着，
   等于无人值守继续烧 LLM。代价：重启即结束会话，要继续得重新开启——这正是想要的。
2. **回滚上限按连续次数计**（原单：连续 2 次回滚到同一 `snapshot_id`）。自动回滚不指定快照，
   `apply_decision` 退回 `scene.snapshot_id_before`；而重演场景的前置快照是开跑时新打的，
   目标 ID 每次都不同，原判据永远不触发。又因为回滚=分叉（08），每次都真的多一条分支，
   所以上限必须在**执行前**判：`make_decision` 的规则化推荐不调 LLM，先算出来、判完再作为
   override 交给 `apply_decision`。
3. **决策点在运行锁释放之后、终态帧之前**。原单放在 `run_scene` 评估之后——那时 `_active_scenes`
   还挂着，`apply_decision` 为 continue 起的新 `run_scene` 会被重复启动守卫静默丢掉。
   终态帧因此从 `run_scene` 的 try 里挪到 finally 之后发；自动 continue 时**不发**这一帧，
   否则迟到的 completed 会让重连上来的客户端把新一轮误判为结束。
4. **停止条件比原单多四条**：评估不可用/补写失败（`make_decision` 对不可用评估给保守默认，
   人工值守时合理，无人值守时就是拿没信息量的评估建场景）、抵达结局（界面上结局不锁按钮，
   无人值守时没人来"不认同"）、`导演中断`（pause 走正常终止路径、场景照样 completed，
   见 CLAUDE.md 12.1）、幂等重放命中人工决策。
5. **前端靠场景流上的 `autopilot` 事件 + 3 秒轮询兜底**，没开项目级 SSE。从已完成场景开启时
   没有流可推，只能靠轮询；刷新恢复也走同一个 GET。跟随只在会话"前进"时发生，
   否则用户在自动推演期间翻看别的场景会被轮询拽回去。

**第一轮 review（审 `806154a`，4 条，全部为真）**，都是"并发登记 / 异步结果提交"的边界，
共同教训：**校验必须和它保护的提交在同一个临界区或同一个同步段里**，事后再查就晚了。

1. **[P1] 开启会话的查重与登记不原子**：两者之间隔着读项目、读场景的 await，并发请求都能过检查。
   加项目级 `_autopilot_lock` 罩住整段。原有幂等测试是顺序调用，覆盖不到。
2. **[P2] 旧跟随响应晚到，把舞台和流切回旧场景**：原实现调 `attachScene`，它内部已经改了舞台和流，
   返回后才查会话是否前进。拆出 `showAttachedScene`，按跟随序号在提交前校验。
3. **[P2] 跟随失败后轮询不重试**：状态先写入、场景才取失败，下一次轮询是同一步、不算"前进"。
   另记 `followTarget`，到达才清——它与"用户主动翻看别处"区分开（后者不会有未完成的目标）。
4. **[P2] 离页后在途轮询复活旧会话**：`resetAutopilot` 只清状态不作废请求。加项目绑定
   （`bindAutopilot`）与生命周期版本。其中轮询回调里的版本检查在"离页"场景下被项目检查兜住，
   变异测试不变红，保留作为同项目离开又回来时的第二道。

均先红后绿（后端 2 个、前端 4 个用例），前三项的保护逐个撤掉均有对应用例变红。

## 工单 07 — 世界状态：三处与工单原文的偏离

工单写于工单 08 / 14 / 26 之前，几条实现建议已经和现行架构对不上。
**结论先行：DoD 全部达成，但实现路径变了三处**，都已征得 owner 确认。

**1. 回滚不走 `restore_snapshot()`（工单 §3.6）。**
该方法自 rollback 改走 `get_snapshot` 后已是 dead code，且 `CLAUDE.md` §12.2 明令
禁止接回写路径 —— 它 `rmtree` 项目级 chroma/kuzu，会抹掉回滚点之后**所有分支**
已积累的长期记忆。改为：`fork_from_snapshot` 把快照里的世界变量搬进新分支
（I3 的同类）。rollback 本就是”条件为空的分叉”，回滚语义因此自动成立，
不需要任何破坏性操作。顺带给 `restore_snapshot()` 加了 `confirm_destructive` 路障 ——
它现在还漏掉世界变量这一维，恢复出来的状态是**半对的**，而半对比全错更难发现。

**2. 合并结果不写回 `Scene.initial_conditions`（工单 §3.3）。**
写回并落库会撞上分叉不变量 I5（`Scene₀.initial_conditions = {**来源场景条件, **C}`）：
那一刻的世界变量快照会被当成**场景局部条件**继承下去，而局部条件的优先级高于世界变量，
于是这条分支上的同名世界变量**再也改不动了**。合并只发生在 `SceneEngine._scene_context()`。

**3. 后置快照需要补写（工单未提及）。**
`world_state_delta` 出自评估，而后置快照在评估之前就打好了。不补写的话，从该快照
分叉出的分支会缺掉本场对世界的改动，而它的角色状态与导演历史都已包含本场 ——
这种”部分维度落后一场”的快照最难排查。新增 `record_world_state`，与
`record_story_history` 共用同一套 meta.json 补写路径。

**实现中发现的真问题（工单的验收条件本来达不到）**：
工单 §3.3 断言”不需要改动 `CharacterAgent`，因为它已经从 `scene_context` 读取信息”。
实际上 `_scene_brief` 只渲染 `name`/`location`/`description`/`opening_narration` 四个键，
其余键**只参与 lore 关键词匹配**，从不进角色视野 —— 导演写了两年的 `initial_conditions`
其实角色一个字都没看到。已改为逐条渲染，顺带修掉这个潜伏缺陷（`CLAUDE.md` §4.2 陷阱 20）。
> 教训：**”已经从某个 dict 读取”不等于”读了这个 dict 里的每一项”。** 把新数据塞进一个
> “反正下游会读”的容器之前，先去看下游到底读了哪几个键。

**红线（后续工单必须保持）**：世界变量进的是**全部在场角色**的 system prompt，
因此只能存放公开事实（契约 1）。工单 20 的环境智能体最容易破这条：动作裁决的结果
天然带私密性（”只有他看见水盆亮了”），沉淀成世界变量前必须先过公开性判据。

**PR #20 review 复盘（五个洞；第 4 条修了两轮，第一轮把窗口起点定错了）**：
细节与修法已写进 `CLAUDE.md` §4.2 陷阱 19 / §6.3.1，这里只记成因与教训。

1. **同分支两场并发，后完成的整份覆盖先完成的**。`_apply_world_delta` 拿的是 `run_scene`
   开场读的副本，中间隔着整场 LLM。`_active_scenes` 只防同一场被启动两次，
   同一分支上的两个不同场景照样能并发。**只给写加锁救不了**，锁只是把过时副本安全地
   写进去 —— 读-改-写的临界区必须从重读开始。
2. **世界变量顶掉场景自己的设定**。世界变量和场景条件摊在同一个 dict 里，世界里存着
   `location=首都` 就会改写本场地点。四个成句键升为保留字，写入 / 合并 / 引擎构造三处拦截，
   且与 `CharacterAgent._BRIEF_KEYS` 共用一个常量，防止两边漂移。
3. **人工编辑的 `world_state/*.json` 绕过预算**。预算闸门只装在导演写入那一侧，而文件
   明确允许手改。补上读取侧的 `clamp_world_variables`，**只压不写回**。
4. **评估 / 补写完成前的分叉会永久丢掉本场世界改动**。分叉只读一次快照里的世界变量，
   之后的补写不会传播过去，而且不像超预算那样有 warning 可查。
   第一轮修复把守卫挂在 `save_scene` 之前，理由是“scene 落库后快照才可见”，这个前提不成立：
   fork 只读 `snapshots` 表，`create_snapshot` 一提交就能分叉。第二轮改为引擎预生成快照 id，
   在创建**之前**经 `on_after_snapshot` 回调挂标记。
   另：`test_fork_during_evaluation_keeps_history_known_at_fork` 原先把“分叉拿到旧数据”
   当作可接受的冻结语义来断言，等于**用测试把缺陷固化了**，现已改为断言窗口内分叉被拒。
   > 教训：**“什么时候可见”要从读取方（fork 读哪张表）倒推，不能从写入方的业务节点推。**
5. **键带换行会凭空多出一条变量**。“一行一条”约束的是**渲染出来的行**，键值同在
   `- {k}：{v}` 一行，只塌值不塌键是做不全的，而三道闸门只按名字判保留字、不看形状。
   顺带把 delta 超条数时的静默截断改为 warning。
   > 教训：原文写的是“把值塌成单行”，漏掉键正是照这句话实现的结果。
   > **约束该按不变量本身（渲染结果）来写，不要按某个实现手段来写**，否则文档会把实现范围框小。

## 工单 29 — 世界设定可见性泄露（实测与取舍）

**怎么发现的**：分析《玻璃王冠》项目里"投影为何不按规则出现"时顺带查了角色卡。
8 条世界设定**全部** `scope=global`，5 张卡各一份，其中有"王后知道伊莎贝尔并非亲生"
"粮仓短缺是王后安排的""王冠读取佩戴者记忆"。种子原文明写了谁不知道哪条。
抽取提示词只给了 global 一种示例、且拿不到角色 ID，分发侧又把 global 发给所有人 ——
**信息不对称在构建那一刻就被抹掉了**，而角色演出时 LLM 常"装作不知道"，从输出看不出来。

**取舍**（细节见工单 §4）：

1. **失败即收紧，不退回 global**。漏一条公开设定的代价远小于泄露一条秘密，且后者无痕。
2. **构建与迁移共用一个分类器**，构建因此多一次调用。若在抽取时顺带判定，迁移就得另写一份，迟早漂移。
3. **证据是各角色的已知/未知事实**，不是种子原文的字面重叠（公开事实与秘密常共用词）。
4. **迁移脚本区分"调用失败"与"判不出"**：前者整个不写、让人重试（构建时没人能重试才只能收紧），
   后者照常收紧。否则一次网络抖动就会把所有设定从所有卡上撤掉。
5. **隐藏设定不另建存储**：目前没有导演侧代码读设定。24 引入物件 / 隐藏规则存储时一并考虑。

**验证**：三处防护逐个撤掉均有用例变红——旧的全员分发（端到端用例：王冠规则进了伊莎贝尔的
prompt）、旧的 `endswith` 读取判定（3 / 4 个 scope 用例）、迁移的"调用失败不写"。

## 工单 24 / 20 — 重新定义：动作 → 环境校验 → 环境回合（2026-10-02 讨论）

**起因**：《玻璃王冠》实测，场景进行中王冠**从未有过反应**：

- 角色反复对王冠做动作（"将王冠举过头顶"），下一轮无人接，甚至出现空回合；
- 角色在动作里**自己替世界宣布结果**（"暗格开启的细微声响…"），因为没有裁决者；
- 两次投影都只出现在导演为**下一场**写的开场白里，且都违反种子规则
  （碰一下就触发、伊莎贝尔戴上却投出王后的记忆）；
- 物件在系统里没有落脚点：图谱只有 Character / Location / Event / Concept，运行时不读图谱。

**MiroFish 的做法（物件当角色发言）为什么不行**：物件会有"意图"、在轮次里抢发言。
**正确形态**：物件是被动规则，触发源是角色动作 ——

```
角色 *戴上王冠*（只写尝试，不写结果）
  → 环境校验：能不能做？会触发什么？（按物件的隐藏规则裁决）
  → 环境回合（公开，进"目前对话"，同【旁白】的位置，不破契约3）
  → 揭示内容三级来源：
     ① 导演预制：规划这一场时写好（"若塞芙拉佩戴 → 襁褓那一夜"），只给导演/环境看，
        不得进 scene_context（陷阱 20：进那个 dict 就是公开）；
     ② 现场生成：只能从**佩戴者自己的** known_facts 与记忆取材，绝不能用其 unknown_facts
        （伊莎贝尔不知道自己非亲生，王冠就不可能从她脑子里投出这件事）；
     ③ 信息不足：只给可观察现象（光幕亮起、画面模糊），内容留给导演在评估/下一场补
```

**拆单**：

- **29（先做）**：设定可见性。物件隐藏规则若走同一条通道，环境层做得再好角色也早知道答案；
  24 的物件抽取也要改 `world_rules.py`，先合 29 免冲突；
- **24**：物件表（名称 / 别名 / 公开描述 / 隐藏规则；构建时抽取、用户可编辑，可见性沿用 29）
  \+ `DialogueTurn.actions`（动作文本先按物件名预过滤，命中才用 selector 小模型抽取 ——
  实测绝大多数 `*动作*` 是神态语气，预过滤能把成本压到很低）。物件的**公开状态**
  （暗格已开、谁戴着）第一版复用 `WorldState`，不另建分支级存储。**24 单独上线没有消费方**，
  与 20 写成一份设计单、分两个 PR；
- **20**：环境校验与反馈。验收用例就是玻璃王冠：伊莎贝尔戴上 → 投她自己的记忆；
  塞芙拉碰一下 → 不触发；暗格须按诺安给的方法才开。

**20 落地时要守住的线**（提前写下，免得 24 的数据结构撑不起）：

- 环境回合用 `DialogueTurn` 表示（如 `kind=environment`），水位线 / 续跑重放 / 在场记忆自动适用；
  但它**不得打乱轮询发言顺序**（现按 `turn_number % 角色数`），也要定它算不算 `max_turns`；
- "动作已落盘、裁决未出"之间崩溃，续跑要能识别"这条动作还没裁决"，不重复、不漏；
- "只写尝试不写结果"的格式规范**必须与 20 同时上线**，只上 24 会让动作悬空无人接；
- 只有当事人能感知的结果只进当事人记忆，不进世界变量（契约1，见 #t07 红线）；
- 环境**主动**事件（"叛军抵达城门"）现在也靠导演在场间写，属后续扩展，不进第一版。

**作废**：工单 11 §2.2 的"动作解析"——它要求环境状态在下一轮 `build_system_prompt` 中体现，破契约 3。

## 工单 22 — MCTS / 多结局

当前是「每次只生成一场 + 采纳导演建议」= 已默认剪枝的贪心单路径，多结局靠人工从快照分叉。
只有当**场景评价与分镜稿都持久化**之后，树上才有可比较的节点价值，搜索才谈得上。
**不要提前上算法。**
**PR #19 review 复盘（五个洞，成因不同；其中第 9、10 条是修复过程中新引入的回归）**：

6. **周期固化会漏写长期记忆却推进完整水位线** —— 五条里最严重，比工单原本要修的缺陷更糟。
   `_should_consolidate` 只问"距上次固化几轮"，不问"缓冲还装得下吗"。固化跨度一旦达到
   `SHORT_TERM_BUFFER_SIZE`，超出部分在到达 `consolidate()` 之前就被定长 deque 挤掉，
   而收尾固化照样把水位线推到 `len(turns)` —— **宣称已入库、实际永久丢失，且无痕**
   （重复写入至少还能被 `check_memory_dupes` 查出来）。
   实测：容量 3 / 周期 20 跑 8 轮 → 只有最后 3 条进库，水位线却是 8。
   根因是上面第 2 条只做了一半：移除 `add_experience` 的自动固化时，接管了"固化"这个
   声明职责，**没接管它顺带承担的"防 deque 溢出"副作用**。我当时意识到了风险——
   `short_term.py` 那条 warning 就是为它写的——但**只加了日志没加机制**。
   修法是两道闸门：`Settings._validate_consolidate_period` 挡住 `周期 >= 容量` 的配置
   （启动即失败，与 `DEFAULT_SPEAKER_MODE` 同理）；`SceneEngine._buffer_under_pressure`
   \+ `ShortTermMemory.pressure()` 按占用率 0.75 在运行时强制固化。后者不可省：周期=0 时
   跨度是整场 `max_turns`，`prime()` 回填又让缓冲开跑即非空，都不是配置校验能覆盖的。
   > 教训：**配置项之间的耦合约束写在注释里等于没写。** `config.py` 里那句"应显著小于
   > SHORT_TERM_BUFFER_SIZE"是对的，但没有任何代码强制它，配成 40 就静默丢数据。
7. **续跑丢失水位线之前那段的事件摘要**。重放起点按 `turns_consolidated` 切，但 episodic 是
   独立内存层、不随长期记忆持久化、与水位线毫无关系，它的正确起点是最后一次快照。
   **该洞在工单 26 之前就存在**，只是那时水位线中途不推进、崩溃时通常为 0，重放恰好覆盖全部
   而掩盖了它——是本单**暴露**而非引入，但既然本单让它变成常见路径，归本单修是对的。
   拆成 `_replay_unconsolidated`：水位线之前只走 `MemoryManager.replay_episodic`
   （补摘要、不写缓冲，否则正文会被下次固化二次写入），之后走完整 `_remember`。
   危害低于第 6 条：episodic 不进角色 prompt（只进快照与 `/inspect` 只读面板），
   且丢的是启发式摘要，原文仍在长期记忆与 `dialogue_log` 里。
8. **固化与日志落盘之间的窗口会留下"日志里还没有的台词"**。Chroma 与 SQLite 是两个库、
   没有跨库事务，这个窗口**无法消除**，能选的只是往哪边失衡：
   - 不管：崩溃后角色记得一句日志里没有的台词（内容真实发生过，不是幻觉，但无兜底）；
   - 反过来先落水位线：崩溃后水位线超前于长期记忆 → 整段永不写入 = 第 6 条的病。

   现改为固化**前**先单独落一次 `dialogue_log`，使窗口内的状态变成"日志有、水位线旧"，
   续跑重放该轮时撞上内容寻址的幂等兜底收敛成一条。**等于把没兜底的失败模式换成有兜底的。**
   代价是每个固化周期多一次 `save_scene`（周期 20 时可忽略）。
   **不能改成把固化挪到 `on_turn` 之后**——那会让 SSE 推送插进固化与落盘之间，破坏 R1。
   附带说明：多角色时 `_consolidate_all` 里的 `for agent` 也可能写到一半被杀，同样靠幂等
   兜底收敛——这说明 §3.2 的兜底层不是"可选的保险"，它是主线设计的一部分。

两处既有断言随之修正（都是被修正的语义，不是迁就实现）：水位线**允许暂时落后**于已产生轮次
（落后有兜底，超前才是 bug），周期轮的 `on_persist` 由 1 次变 2 次。
测试 242 passed（原 237 + 新增 5）。

9. **第 7 条的修法自己带进了一个回归：正常 continue 会把那段事件摘要追加第二遍。**
   契约4 的四级优先级里，正常 continue 命中的是 `snapshot_id_after`（本场上次跑完时打的），
   它的 `episodic_summary` 已含 `[0, turns_consolidated)` 的全部事件，`build_character_agents`
   又已 `prime()` 载入；我的重放循环逐轮 `record()` 再追加一遍，而 `record()` 无去重、
   `build_summary()` 只保留 `_events[-10:]` —— 于是**更早场次**的重要事件被挤出窗口。
   实测：上一场 4 条 + 本场 6 条（正好满窗）→ 续跑后 `_events` 10→16，上一场 4 条全部蒸发、
   4 行重复。episodic 不落盘、无脚本可查，挤掉就是永久丢失，**比第 7 条原本要修的"缺一段"更糟**
   （那至少是可预期的缺失，这是静默覆盖）。
   **我漏掉的是一个不对称**：崩溃续跑（prime 来自 `snapshot_id_before`，不含本场）需要重放，
   正常 continue（prime 来自 `snapshot_id_after`，已含本场）不需要；而那段代码分辨不了两者。
   修法**不是**去判断快照来源 —— 还有第三种情况：continue 续跑到一半再崩，`snapshot_id_after`
   只覆盖前半段，按来源二分会漏掉后半段。改成 `EpisodicMemory.replay(turns)`：
   **整批传入、按正文剔除本批已存在的条目、再按日志顺序整段追加**，让"全含 / 全不含 / 只含
   前半段"三种来源收敛到同一终态。接口也从"逐轮"改成"整批"，让调用方无法再写出逐条追加。
   语义与长期记忆的内容寻址兜底一致（同一角色说出完全相同的一句话会合并成一条）。
   > 教训：**去重兜底要按层配**。长期记忆有了内容寻址就以为重复写入的问题整体解决了，
   > 但 episodic 是另一层、另一套存储（纯内存 + 定长窗口），它一条兜底也没有。
   > 第 7 条给它补了"会丢"，没补"会重"——而定长窗口让"重"直接等价于"丢"。

测试 245 passed（新增 3：引擎级 continue 重放不挤占 + `replay` 幂等与顺序 + 契约1 独白剥离）。

10. **上一条的去重按整行比对，而条目正文可能带换行 —— 往返不恒等。**
    摘要是"一行一条"序列化的（`dump` 用 `\n` join、`load` 用 `\n` split），但
    `SceneEngine._parse_turn` 的动作正则带 `re.DOTALL`，跨行的 `*动作*` 会产出含 `\n` 的
    `action`（对白早就被 `re.sub(r"\s+", " ")` 规整过了，**只有动作漏了这道**）。
    于是一条事件 `record` 进去是 1 条、存进快照再 `load` 出来是 2 条，与重放生成的单条
    对不上 → 去重失效 → 实测 `record→dump→load→replay` 后条目从 1 条**涨到 3 条**，
    并多占 `_events[-10:]` 的保留窗口挤掉更早的事件。第 9 条修的是"重放翻倍"，
    这是同一个窗口被从另一个方向占掉。
    修法统一在序列化格式上：`_normalize_entry` 把条目正文里的换行/连续空白塌成空格
    （在唯一的渲染点 `_snippet` 里调用），`load` 则按 `[重要] ` 前缀识别条目行、
    **把不以前缀开头的续行并回上一条**。老快照里已有的多行条目因此能收敛到与新渲染
    完全一致的单条，**不需要迁移脚本**。
    > 教训：**"按内容去重"隐含了"内容有唯一规范形式"这个前提。** 长期记忆的 sha256
    > 寻址同样吃这个前提，只是它的输入（`_turn_to_text`）恰好没有换行问题。
    > 去重键的规范化必须和序列化格式一起定，不能分开想。

测试 247 passed（再新增 2：`record→dump→load→replay` 往返恒等 + 老多行快照并回）。
